# Git execution route

This is the repository-owned entry point for Git command launch and transport.
Use it for Git work, not ordinary task entry. A template copy defines the
contract; it supplies no configured route, live acceptance or action authority.

## Select the route

Before the first applicable Git operation, check the current repository's
documented route and its evidence. Reuse a qualified route only for its recorded
device, runtime, effective profile, helper revision and operation. Resolve an
existing project-owned guide/helper here instead of duplicating or replacing it.
Read-only inspection normally remains sandboxed. If no special route is recorded,
use ordinary Git under the local authority and execution rules; do not invent
an adapter, install tools or run a qualification matrix as a prerequisite.

Distinguish these three requirements:

- The maintainer authorizes the exact repository/action and publication scope.
- The platform approves the necessary execution boundary for that operation.
- Evidence establishes that the selected command route actually works there.

One does not supply the others. Use the required narrow escalation on the first
authorized metadata write. Apply it to the complete reviewed launcher invocation
when that is the qualified route. An approval rejection is not permission to
repackage the same denied action through a child process or another tool.

## Retain one usable route

When setup or an authorized repair establishes a special route, maintain this
guide as its durable owner. Link the reviewed helper/source and the accepted
invocation, including the launcher; an SSH setting alone is insufficient.
Keep non-secret device bindings in ignored `GIT_TRANSPORT.local.md` when needed,
or link an existing approved local record without duplicating it. Read only
assistant-authorized metadata. Never include keys, tokens, protected filenames
or raw credential/worker diagnostics. A guide link grants no referenced access.

Record only what a later skill needs:

- Repository identity, verified destination and supported operations; exact
  executable/helper entry point, argument form and working directory.
- Device/runtime/profile, reviewed helper revision, authentication mechanism
  and safe configuration references; keep machine paths and bindings local.
- Prerequisites, required execution approval, timeout and permitted output.
  Preserve argument boundaries, Git exit status, hooks and signing. Do not
  replace a failed signed/hooked operation with an unsigned or hook-free one.
- Dated per-operation evidence and its limits; distinguish PASS, FAIL,
  NOT_TESTED and explicitly excluded NOT_APPLICABLE. Keep failed evidence.
- Exact owned configuration delta, original values and recovery/revocation
  procedure. Installation, credential provisioning and recovery writes retain
  their own authority; the guide grants no standing permission.

## Qualify and reuse proportionately

Separate local read, exact staging, commit, annotated tag, authenticated remote
read, fetch, fast-forward integration and push as applicable to the workflow.
A successful fetch or remote test ref does not establish local commit capability;
a successful stage does not establish commit, hooks or signing. A no-op push
does not qualify a remote write. A host control is not protected-runtime success.

During selected setup or repair, use the smallest authorized non-sensitive
operation in the intended runtime. A requested real operation may supply its
own acceptance; verify its exact resulting index, commit/tag or remote ref.
Do not create commits/tags or remote test refs merely to fill a table without
their specific authority. Temporary remote trials require an agreed absent ref,
expected-value cleanup and independent absence verification. Preserve unrelated
staging, branches, refs and profile settings. Mark missing authority/evidence
pending; source review and fake tools are not live qualification.

Reuse unchanged evidence. Reassess only affected operations after a material
runtime, effective-profile, launcher/helper, authentication, destination or
hook/signing change. Do not silently fall back to a different boundary or device.
For a clear failure, use `reuse-fixes`, consult the local route before repeating
the launch, and resume at the original operation within existing authority.
After an uncertain outcome, inspect authorized result metadata before retrying
so an interrupted report does not duplicate a successful mutation.

Hand terminal work back to the maintainer only when a concrete access boundary,
missing authority or unresolved capability blocks the authorized route. Report
the failed operation and smallest remaining step. Never remove file denies,
expose credentials or treat a wrapper as a policy bypass. Reviewer selection
and configuration changes are separate from route capability.

## Domain boundary

Preserve the selected engineering toolchain and project-owned hooks/signing.
