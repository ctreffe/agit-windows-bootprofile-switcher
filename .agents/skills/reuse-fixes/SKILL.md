# Reuse Fixes

Reuse confirmed fixes and retain useful prevention in the current repository.
Ordinary debugging stays with its owning task; this skill supplies repository
experience for clear access, authorization or setup problems and recurring
execution mistakes.

Preserve dependency, engineering, test, release and sensitive-input boundaries.

## Reuse and recover

Search `TROUBLESHOOTING.md` for the observed signature before repeating a failed
approach. Read only a matching compact entry and relevant host-local facts.
Consult only the matching section in `TROUBLESHOOTING_DETAILS.md` if needed to
resolve applicability, safety or verification; do not load both files by default.
Preserved details are historical evidence, not current instructions. Check current
applicability; use a safe diagnostic when needed. Historical evidence is not
proof of readiness on a new clone or device.

Apply a confirmed correction or a bounded, reversible task-local fix within
existing authority, then continue the original operation at its exact checkpoint.
Retry unchanged once only when plausibly transient; otherwise require new
evidence before another attempt. Do not show a mandatory route-choice menu or
stop unrelated work.

Known permission boundaries need the correct execution path, not a new incident.
Reuse granted action authority and request exact platform escalation when needed.
Ask only for missing authority or a material decision blocking the next action.
When a control word is required, provide one minimal copy-ready instruction
naming the exact action, repository and material consequence; the proposal is
not authorization. No recorded fix grants access, installation, privilege,
global configuration, transmission or protected Git authority.

For a standalone request, use the requested normal operation as the concrete
acceptance test; clarify only if success is ambiguous. Do not write a fix-specific
test or treat diagnostic success as recovery. A failed correction is new
evidence, not a reason to repeat the same approach.

## Retain prevention

After verified recovery, update an existing entry or add one useful entry in
`TROUBLESHOOTING.md` using 4–8 nonblank source lines, including the stable KI
heading: **Recognize**, **Fix**, **Prevent or limit**. Keep necessary applicability
and authority limits in these fields. Dates, causes and diagnostics are optional
when they change the next action; detailed reports and transcripts are not required.
Retain a matching evidence link when available. Add detail only when useful.
Do not log every recurrence or transient retry. Label a verified local adaptation's
limits; do not claim permanent environment repair without evidence.

Keep host paths and identifiers in `TROUBLESHOOTING.local.md`. Never record secrets, protected
content or an unverified correction as successful. Retain an unresolved case's
smallest next step only when useful. Promote essential prevention into a relevant
task instruction only within authorized scope; policy changes remain maintainer
decisions.

Use only this repository's records. Do not inspect other repositories' error
records, synchronize lessons, or build or consult user-global memory. Personal
cross-repository learning is controlled separately by the user. Report the
recovery and retained lesson briefly, then continue the task.
